Tasks and Runs — six ways to split the app

information architecture, not row design · prior art named per variation

The overlap is real and it is structural. A Task is a definition; a Run is an instance of it. Every product with that duality has had to answer the same question, and they have answered it in about six distinguishable ways. Each frame below is one of those answers, wearing Spring Roll's clothes.

The question underneath yours: is this a reading product or an operations product? Operations tools (Jenkins, Airflow) make the definition list home, because you are watching for failure. Reading tools (an RSS reader, a podcast app, Google Alerts) make the output stream home, because the content is the point and the definitions are a settings screen you visit twice a year. Spring Roll produces daily reports you actually read — but its homepage is currently the definition list.

The evidence that the two pages are colliding. The Runs row already carries an excerpt of the report (Outputs.excerpt_line/1), and its own source comment says the row "mirrors a Tasks row: title line, then one sentence under it." The Tasks row, meanwhile, is mostly run data — last status, failure date, seven days of bars. Each page is drifting toward the other because neither one owns the question "how did today go?"

And the cardinality is lopsided: this workspace has 7 tasks and 140 runs. A page for seven items isn't a page, it's a settings screen. A page for 140 growing items is a real surface.

1 · Feed first — the output stream is home, tasks become a library

Prior art: NetNewsWire / Reeder (feeds vs articles) · Overcast (shows vs episodes) · Google Alerts (you manage alerts once, you read results in your inbox forever)

"Runs" stops being a word in the product. What lands here is a report, titled with its own headline, attributed to the task that produced it. Unread state does the work the seven bars were trying to do. Tasks move to a Library screen you visit when you want to change something.

2 · Task-first, runs nested — there is no global Runs page at all

Prior art: GitHub Actions (workflows in the sidebar, that workflow's runs in the main pane — no top-level runs page) · Airflow (DAG list → that DAG's history) · Jenkins (job → builds)

Runs stop being a peer of Tasks and become a property of one. You always arrive at a run through the task that made it. The nav loses an item, and the ambiguity goes with it.

3 · One list, two lenses — merge the nav items, keep both readings

Prior art: Sentry (an Issue is the grouped thing, an Event is the instance — one list, you drill in) · Linear (same issues, grouped or flat by a toggle)

Tasks and Runs stop being two pages and become two groupings of one dataset. "By task" collapses every run under its definition — that view is the Tasks page. "By time" flattens them — that view is the Runs page. Same URL, same rows, one nav item.

4 · Today / Library — split by intent, not by object

Prior art: Things 3 and Apple Reminders (a repeating to-do is a definition; "Today" shows only the instances due now, and the project list is elsewhere) · Todoist Today vs Projects

The todo apps faced this identical duality — recurring definition vs today's instance — and resolved it by making the home screen a time slice rather than an object type. Today mixes finished output, problems, and what's coming. Everything else is Library.

5 · One composed brief — the most radical: the home page is a document

Fixes: makes the product's value visible in the first three seconds, which no list of task names ever will. It is also the most defensible thing to show someone else — the edition is the product, the scheduling machinery is plumbing.

Costs: the most work and the most fragile — composing an edition means summarizing summaries, which is another model call and another thing to get wrong. Bad on a day when one task ran. Worth prototyping as a view over direction 4's data before committing to it as the home page.

6 · Keep both, sharpen the boundary — the smallest possible change

Prior art: Healthchecks.io and Cronitor (a checks list is pure health — status pings, last ping, next expected; the payload lives elsewhere) paired with any reader

If the two pages stay, they need a rule they don't currently have: Reports owns content, Tasks owns health and configuration — and neither shows the other's data. That means stripping excerpts and failure text out of Tasks entirely, leaving uptime, cost and next fire. It also means Reports, not Tasks, is /.

My read: 6 is the honest minimum and can ship this week — it is mostly deletion plus swapping which page is /. 4 is where this wants to end up, because "Today" is the only home that answers the morning question without inventing a summarization step. 1 is the same idea with a different emphasis and is worth considering if you decide reports should carry their own headlines. 5 is the most compelling demo and the least safe default. 2 is the wrong shape for a reading product, and 3 buys tidiness at the price of a vague home.

The question that decides it: when you open Spring Roll in the morning, are you checking that the machinery ran, or reading what it found? If it is the second, the definition list should not be the front door.
