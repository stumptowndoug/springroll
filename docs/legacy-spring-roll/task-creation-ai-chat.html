Revised direction · Inline task creation

“New task” is a small natural-language control, not a destination.

The Tasks page stays the Tasks page. Clicking the button opens one compact prompt in place. It grows only when Spring Roll needs a clarification, collapses into a reviewable proposal, then disappears after the Task is created.

The important distinction: this is not a chat product. It is a natural-language replacement for a creation form. Conversation is a temporary input method attached to one action—not the app’s navigation, identity, or default layout.

The shape of the interaction

The component should feel closer to Spotlight, Linear’s command menu, or an expanding Notion block than to ChatGPT.

Default path: click New task → type one sentence → see a proposal → Create. The clarification state is an exception for missing schedule, ambiguous destination, unavailable connection, or risky behavior—not a ritual the AI performs every time.
01Stay on the Tasks page

Do not navigate to /tasks/new for the normal flow. Expanding and collapsing the composer should not disturb scroll position or the task list.

02Do not render a transcript

Keep only the user’s current request and Spring Roll’s current clarification. Once resolved, replace both with the proposal. The interaction is state, not conversation history.

03Expand downward

The component begins one line high and grows to a sensible cap. If authoring becomes unusually complex, “Continue setup” may open a focused sheet—but never reorient the whole application.

04Use defaults aggressively

Infer name, slug, instructions, output shape, model, and notification policy. Ask only when the answer materially changes what runs or where data goes.

05Confirm facts, not fields

Show “Weekdays at 8:00 AM · America/Los_Angeles · web access · one Markdown brief.” “Change something” returns to one natural-language line.

06Disappear when done

After creation, collapse the component and insert the new Task row with a subtle highlight. The permanent artifact is the Task, not the chat.

This is

  • A contextual natural-language control.
  • A temporary replacement for the New Task form.
  • A thin AI interpretation step over deterministic validation.
  • Optimized for one prompt and zero or one clarifications.

This is not

  • A general assistant in Spring Roll.
  • A chat page, inbox, thread list, or saved conversation.
  • A reason to change the Tasks/Run information architecture.
  • A substitute for the user’s preferred external chat app.

Implementation plan

This is simpler than a full conversational authoring surface. Treat it as one stateful component on TaskLive.Index.

1 · Inline UI state

  • Replace the navigate={~p"/tasks/new"} action with phx-click="open-task-composer".
  • Add assigns for :composer_state, :task_request, :clarification, :candidate, and :authoring_error.
  • Render the composer immediately below the page header and above the task stream.

2 · One-shot interpreter

  • Send the English request through SpringRoll.Pi.Completions with workspace defaults and available capabilities.
  • Require a versioned structured result: candidate patch, optional single clarification, and short suggested answers.
  • Run the completion asynchronously so the task list remains live and usable.

3 · Deterministic candidate

  • Merge model output into server-owned defaults and validate using existing ScheduleSpec, OutputContract, model, MCP, extension, slug, and environment rules.
  • Render the compact proposal from normalized server data—not assistant prose.
  • If validation can be repaired with one consequential answer, ask it inline. Otherwise show a concise retry state.

4 · Explicit creation

  • Commit only after the user clicks Create task, via the existing Tasks.create_skill/2 path.
  • On success, use the existing Task broadcast/stream refresh, collapse the composer, and briefly highlight the inserted row.
  • Keep /tasks/new temporarily as a feature-flagged fallback, not the primary path.

5 · Narrow tests

  • Test closed → prompt → generating → clarification/proposal → created transitions by stable DOM IDs.
  • Cover provider failure, malformed model output, unavailable integrations, duplicate slug, cancel, and double-submit.
  • Measure prompts per successful Task and clarification rate; the goal is close to one prompt per creation.

Recommendation

Build the four-state inline composer

Keep the entire experience attached to the existing New task button. Cap the normal interaction at roughly 480–640px wide and one to four lines tall, expanding vertically only for one clarification or the final proposal.

The product rule should be: English in, Task out. No chat destination, no transcript, no assistant identity competing with the rest of Spring Roll.

One useful escape hatch

If a request truly needs several decisions, show “Continue setup” and expand into a temporary sheet over the same page. That is a pressure release valve, not the default interface—and it should still collapse back into a Task proposal when finished.
