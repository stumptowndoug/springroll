Chat threshold study · supersedes the dock premise · 2026-07-24

Full page is the answer. The work is the threshold, the way back, and the record.

When you press Enter in the berth, the conversation takes the whole page — and it should: answers carry markdown, charts, proposal cards; they deserve the room. What’s missing is not a smaller chat. It’s that the chat page doesn’t say where you came from, there is no graceful way back while the agent works, and nothing afterward remembers that the conversation belonged to that task.

Three questions, one section each: the threshold — how the chat page declares its origin (T1–T3); the way back — what “minimize” means when chat is a page, not a panel (H1–H3); the record — where the session ↔ page relationship lives afterward (R1–R2). Recommendation: T1 · H2 · R1, assembled in “The pick.” The instruments question from the dock study dissolves — the full chat page already carries the model picker and the usage line.

§2The way back — what “minimize” means for a page

You asked, the agent is working, and you want the task page back while it thinks. Leaving is easy — the crumb, the rail, back. The question is what the origin page shows while its conversation is still alive, so returning is one gesture and a finished answer can’t land unseen.

H1the band becomes the handle
Skip weekends — writing the proposal… return ⏎

On the origin page, the band itself turns into the live conversation: pulsing dot, name, current activity; Enter returns to it. Unmissable — but the band’s one job everywhere is “start here,” and this steals that job. Asking a second question about the same task now needs a different door.

H2the moor linerecommended
Skip weekends— writing the proposal…return ⌃
❯Ask about this task…

One 10.5px mono line above the band, on the origin page only, only while its conversation lives: run-dot, name, what the agent is doing now, return. When the answer lands the dot turns ok-green and the line reads “answered · return ⌃” until visited. The band beneath stays a fresh start.

H3no handle — the rail remembers
tasks chat
❯Ask about this task…

Nothing on the page at all; the rail’s chat room gets the heartbeat’s halo-dot while any conversation streams. Most subtractive — but the signal is global (“some chat, somewhere”) and page-blind, and a landed answer shows nowhere once streaming ends.

H2. It answers “super easy to minimize” by making minimize nothing special — you just leave, and the page keeps a one-line mooring to the conversation you left. It borrows only existing vocabulary: the heartbeat’s dot grammar, the status line’s mono voice, the berth’s column. And it dies quietly: conversation idle and read → the line is gone. If even this feels like furniture in practice, H3 is the honest fallback — the two compose (H2 on the origin page, rail dot everywhere else) without conflict.

§3The record — the relationship, afterward

Next week, the conversation should still be findable from both ends: the task should list what’s been discussed about it, and the chat history should say what each session was about. Both reuse the shipped history grammar — name + age, nothing more.

§5Ledger — what this asks of the code

  • Sessions get an origin. The berth handoff (sessionStorage + send-berth-message) grows a page_context payload — task_id / run_id / folder — persisted on the session. This is chunk 2’s machinery; the study only decides how it shows.
  • T1: ChatLive’s breadcrumb roots at the origin when the session has one (Morning digest › name, root links to the task) and stays Chat › name otherwise. The from-stamp renders above the first turn from the same field.
  • H2: the moor line renders in the berth slot of the origin page only, driven by the same PubSub topics ChatLive already subscribes to (activity label while streaming, answered-state after; gone when idle and visited). No new processes — it’s a read-only listener on an existing conversation.
  • R1: task detail queries sessions by origin task_id (Conversations section, shipped history row grammar); /chat’s Earlier rows render the origin chip when present.
  • Instruments: no work. Full-page chat already carries the split status line — usage, cost, context %, model picker. The dock study’s §3 is moot in this flow.
  • Mobile: no special case. Full-page chat is the native mobile shape; the moor line rides above the band in the same thumb zone.
  • Open picks: does the moor line follow the origin object (this task, wherever listed) or the origin page only (proposed: page only — the object’s memory is the Conversations section)? Should Esc on the chat page act as “back to origin” (proposed: no keybinding yet; the crumb is enough until asked for)? One live moor line max per page, or stack when two conversations about it run (proposed: newest wins, count on the line: “2 live”)?
