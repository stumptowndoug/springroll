Spring Roll · Design system · v3

Absolute simplicity.

v3 is what the Tasks page taught us. The ledger — borderless rows, five run dots, one line of type per task — turned out to be the whole aesthetic: content set directly on the page, navigation reduced to five small-caps words, chrome approaching zero. v2's rules mostly held; v3 tightens the ones the Tasks page proved too generous. Users should feel comfortable, not managed: minimal distractions, no boxes to parse, nothing that moves or shouts unless it is information.

Principles

Every visual decision below derives from these eight. When a new page or component needs a call this guide doesn't cover, make the call that keeps these true — and when in doubt, apply 01.

01

Subtract first.

Before styling an element, ask whether it should exist. The sidebar became five words; the theme toggle became a settings row; the hover row disappeared from mobile. Every surviving element must be data, a control, or a boundary the eye genuinely needs — everything else is a distraction to remove.

02

The content is the interface.

Chrome recedes; tasks, runs, and logs advance. The ledger is the model: rows sit directly on the page ground with no card, no divider, no container — the row's own hover wash is the only announcement that it is interactive.

03

Tone replaces lines — except the frame.

Inside the content, separation comes from space first, then a change of ground (bg-2), and only as a last resort a hairline. The app frame is the exception (revised 2026-07-17, after Medium): the sticky header carries one border hairline on its bottom edge and the side rail one on its right, so the chrome reads as a fixed shell without a second surface color. Those two lines are the frame's entire budget. Inputs keep border-strong — "fillable" is the one earned border inside the content.

04

Color is state.

The palette decorates nothing. Green means healthy or succeeded, carrot means in flight, chili means failed, peanut means money. If something is colored, it is information — everything else is ink on ground.

05

Everything is a token.

One variable sheet drives both schemes; components reference tokens only — colors, radii, shadows, and now type sizes (--text-* scales with the user's preference). If a design change can't be made by editing a token, the component is wrong, not the sheet.

06

Mono means code, not numbers.

JetBrains Mono is reserved for text a machine must read back verbatim: code, tool payloads, IDs and slugs, cron expressions, env keys, file paths, media types. It is NOT an authorship signal — in an app where the agent writes everything, a typeface can't mark "the agent said this" (narrowed 2026-07-15; the old rule set every timestamp and cost in mono, which made mono mean nothing). Figures — times, durations, costs, tokens — are the sans face with tabular-nums, which keeps columns aligned without the teletype look. Prose is never mono; agent prose in document contexts (the run detail body) may wear the reader serif, but never in list chrome.

07

Icons must earn their place.

Words first: navigation needed none, and most labels don't either. An icon appears only where it adds recognition a word can't afford (a compact glyph button, a status mark). The set is Lucide (lucide-*), always a bare glyph — never a background well, tile, or badge behind it.

08

Comfort on every device.

Hover is a desktop luxury. Touch gets no tooltips and no hover reveals, so nothing may depend on either: every hover affordance ships with a mobile answer — always visible, deliberately hidden, or an explicit control. Touch targets are ≥40px; desktop may tighten to 32px.

Navigation — the masthead

Navigation is typography, not furniture. The five destinations sit centered in the running-head position as letterspaced small caps; the current page carries the only ink. No rail, no bar, no dock — the app's map costs zero pixels of chrome.

  • Desktop: the masthead renders on every page, above the (optional) running head. Active state is marked client-side by the .NavActive hook (data-active); active = text-ink font-semibold, rest = text-faint, hover = text-muted. No underlines, washes, or pills.
  • Mobile: the masthead yields to a menu button (Lucide menu) set in a three-column grid — 3.5rem | title | 3.5rem — so the trigger and the centered page title share one row and one vertical center. The menu opens a small word list over a scrim; navigation closes it naturally.
  • The running head is the mobile page title and shares the masthead's small-caps voice. Desktop-redundant plain titles hide at sm:; contextual heads (folder back-links) show at every width.
  • Global preferences own no chrome: theme switching lives on the settings page only and defaults to system. Nothing app-wide floats in a corner.

Color

Grounds and greys follow named references, measured from their live homepages (2026-07-18): light reads like Medium and Notion — true white page, Notion's warm well and warm secondary grey, Medium's ink; dark follows Obsidian — deep neutral ground, neutral greys. Every text token has a computed contrast floor: ink ~15:1, muted ≥6:1, faint ~3.5–4.5:1 and never running words. State colors carry over untouched: their meaning is a contract with every screenshot ever taken.

Rules
  • Green is both brand and success — deliberately. Healthy is Spring Roll's default state, so the brand color and the succeeded color agree. Never introduce a second decorative hue.
  • Tinted fills come from the formula, not new hexes: tag backgrounds are color-mix(state 11%, bg), tag text color-mix(state 78%, ink), failure callouts color-mix(fail 8%, bg).
  • Chili appears only when something is wrong. Destructive buttons borrow it as plain text; a filled chili element means a failure exists right now.
  • The green splits into two jobs: accent #3F8F63 is the mark — dots, links, focus rings, active states; accent-fill #357953 is the workhorse for filled buttons carrying white text; accent-text #2D6A48 is green rendered as text or links. Never put white text on the light accent.
  • Hover is a token, not a guess: interactive surfaces tint with --hover (ink at 6%), pressed with --active (10%). No component invents its own hover color.
  • Greys are warm in light, neutral in dark. Light greys keep Notion's warm cast (muted #615D59, faint #85837A); dark greys are strictly neutral after Obsidian (#B3B3B3, #8A8A8A). When adding or changing a text color, compute the contrast ratio against bg — never eyeball it.

Typography

Type is user-configurable and token-driven. The reader chooses the human face (Inter, Source Serif 4 "reader", or system) and the text scale; components consume semantic sizes (--text-micro / -supporting / -body → text-xs / -sm / -base) and never hard-code pixels. JetBrains Mono appears only where text is literally code (see the code role below); figures stay sans with tabular-nums. New in v3: the furniture role.

Rules
  • Furniture speaks small caps. The masthead nav, running heads, and any future page-level wayfinding share one voice: text-xs uppercase tracking-[0.08em], faint at rest, ink for the current thing. Small caps is the strongest "chrome, not content" signal typography sends without color or surfaces — use it instead of bars.
  • Respect the reader's hand on the dial. All sizes derive from --text-scale and the family from data-font-family. A component that hard-codes px type breaks the preference system.
  • JetBrains Mono is code, not a style — and numbers aren't code. Mono only for text a machine must read back: code blocks, payloads, IDs/slugs, cron, env keys, paths, media types. Timestamps, durations, costs, and token counts are sans + tabular-nums. If a human (or the agent, in prose) wrote the words, they're not mono — even in tables. Exceptions that stay mono: kbd keystroke chips and the event log, which is a literal machine transcript.
  • Hierarchy is weight and tone within one family. Ink 500/600 for what matters, muted 400 for support, faint for furniture — before ever changing size.
  • Nav and furniture words are lowercase in source ("tasks", "new task") and shaped by CSS — the app's voice stays lowercase even when the rendering is caps.

Geometry & separation

Flat by default, and now nearly line-free. The separation ladder is: space → tone → hairline, in that order, stopping at the first rung that works. Elevation exists only for the moment something floats.

Rules
  • No borders wherever possible. Lists are ledgers: rows directly on the page, separated by padding alone, hover wash as the affordance — no card, no divider, no container box. This is the Tasks page pattern and the default for every list.
  • Chrome surfaces are tonal: anything that must read as "not content" (a well, a code block, a guard panel, a menu) sits on bg-2 with no outline. A hairline appears only where space and tone both genuinely fail.
  • Inputs keep border-strong — the one border with a job: it says "fillable." Focus swaps it to accent with a 3px 16% ring.
  • Shadows mean "floating," never "important." shadow-pop for menus, popovers, dialogs, toasts; shadow-raise for a surface responding to drag. Nothing casts a shadow at rest.
  • Circles are for status dots and avatars. Everything else is 4px or 6px — no pills, no full-round chrome.

Icons

Mobile & touch

The same design, not a second one — but honest about what touch lacks. Every rule here came from a real Tasks-page bug: a hover reveal that showed permanently, a tooltip that never fired, a floating button that missed the title's baseline.

  • Hover-gated things need a verdict below lg:. A hover reveal on touch renders permanently — decide per element: always show it, hide it (hidden lg:flex), or replace it with an explicit control. Never let the default leak through.
  • Tooltips (title=) are desktop-only garnish. Anything that needs one to be understood is under-designed for mobile.
  • Targets: ≥40px (min-h-10 min-w-10) on touch, tightening to 32px (lg:min-h-8) on desktop. Glyphs stay 16–20px inside those targets.
  • Header elements share one grid row. Nothing floats with position: fixed next to in-flow text — the menu trigger, title, and any actions align on one baseline via the 3.5rem | 1fr | 3.5rem head grid.
  • Settings behave identically at every width. A preference that only takes effect on desktop (flat/grouped once did) is a bug, not a design decision.
  • Wide content scrolls inside itself; schedule/meta lines wrap to a second row under the title rather than truncating the task name.

Voice

Calm, specific, lightly warm, lowercase where the interface speaks for itself. The product states facts and next actions; it never apologizes theatrically, never exclaims about errors, and saves its small warmth for moments when nothing is wrong.

Sounds like Spring Roll

  • "Everything is quiet. The next run starts tomorrow at 8:00."
  • "Weekly report failed at 9:00 (exit 1). Check the run log, then retry."
  • "This task is paused — nothing runs until you resume it."
  • nav and furniture words stay lowercase: tasks, runs, new task, menu.

Doesn't

  • "Oops! Something went wrong 😢" — vague, cutesy about a failure.
  • "Task execution terminated with non-zero exit status." — raw log-speak in a summary. Quote the machine in mono, explain in the human face.
  • "Supercharge your AI workflows!" — hype voice, anywhere.
  • Jokes inside the timeline, run detail, or any failure surface.

Dark scheme

Dark is a first-class sibling, not an inversion: a deep neutral ground after Obsidian's site (2026-07-18 — #0f0f0f page, #1f1f1f wells, strictly neutral greys where light mode's are warm), the same token names, state colors lifted just enough to keep contrast. The user chooses in settings — system by default — and nothing else in the chrome mentions it.
