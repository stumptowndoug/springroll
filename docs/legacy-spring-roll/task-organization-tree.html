Task design · Organization

A tree for where Tasks belong—not another hierarchy for how they run.

As the Task list grows, a flat alphabetical view stops answering a basic question: “Where does this work live?” Spring Roll should add lightweight, user-defined folders such as Marketing, Operations, and Engineering while keeping Task and Run as the product’s only operational nouns.

Recommendation: add a virtual folder navigator inside the Tasks page. Folders organize; Tasks execute. Keep task bundles physically flat, store the folder as portable metadata, and treat tags and saved views as later, orthogonal tools.

Three directions

Each direction uses the same arbitrary groups. The difference is whether the tree is a navigator, the list itself, or a secondary filter.

A · Folder navigator + filtered Task list

The tree is always available without turning Tasks into files. It scales from three folders to dozens, preserves the polished row design, and gives “All tasks” and “Unfiled” stable homes.

Responsive behavior

On narrow screens, the tree becomes a single folder bar above the list. Tapping it opens a drawer with the same tree; the task rows retain the full width.

C · Linear-style grouped views

Folders become one grouping option alongside status, schedule, and readiness. This is strong when users frequently reorganize the same Tasks for different questions.

Tradeoff

It solves analysis better than navigation. The folder tree is no longer continuously available, and saved views add a concept Spring Roll does not need yet.

What to borrow—and what not to borrow

The strongest direction combines Obsidian's spatial clarity, Notion's collapsible navigation, and Linear's discipline about separating organizational scope from work objects.

Product principles

Folders organize; they do not execute

No folder schedule, enabled state, model, notification policy, Run history, or inherited configuration in the first version.

Tasks are always leaves

Never nest a Task under another Task. That implies dependencies or workflows, which belong to a different execution model.

Location is not identity

Task IDs and slugs remain stable when moved. Existing workflow and MCP references continue to use the slug.

One home, many lenses

A Task has one folder path. Tags can cross-cut later; a Task should not appear to live in multiple folders.

Unfiled is a real place

Imported, legacy, and newly created Tasks without a folder remain easy to find and can be organized in batches.

Flat by default

Do not force organization. Users with five Tasks see essentially today's list; the navigator earns its space as scale increases.

Recommended information model

The app already parses and persists a group string and tags array on each Task. That makes a useful first version much smaller than adding a new folder table.

Portable Task metadata metadata: springroll: group: "Marketing/Content" tags: ["customer-facing", "weekly"] Database projection tasks.group = "Marketing/Content" tasks.tags = ["customer-facing", "weekly"] Filesystem remains flat tasks/weekly-content-opportunities/SKILL.md

Why a path string first

  • It works with the existing Task schema and TaskLoader.
  • It remains portable in a SKILL.md bundle.
  • Folders can be derived by splitting on /; empty group means Unfiled.
  • Moving a Task changes metadata, not its slug or physical bundle path.
  • No empty-folder persistence, custom order, colors, permissions, or folder settings until users need them.
Name in the UI

Call the concept Folders, even though the existing storage field is group. “Group” reads like a temporary view operation; “folder” communicates one stable home and supports a tree naturally.

Path rules

Trim segments; reject empty segments, ., .., control characters, and leading/trailing slashes. Preserve human casing for display. Compare paths case-insensitively to avoid duplicate-looking folders.

Depth

Support up to four folder segments for portability, but design and examples around one or two. Beyond that, collapse intermediate paths and encourage tags instead.

Counts

Parent folder counts include all descendants. The selected folder includes descendant Tasks by default, with an optional “This folder only” filter if needed later.

Ordering

Folders alphabetical first; Tasks retain their current name ordering. Do not add manual ordering until there is evidence it matters.

Creation

New Task inherits the currently selected folder. The future inline natural-language composer may infer a folder only when the destination is explicit; otherwise it uses the current folder or Unfiled.

Phased implementation plan

Start by exposing organization that the data model already understands. Delay richer folder identity until the DB-canonical Task-storage decision is complete.

1 · Read-only tree

  • Build a pure TaskFolders module that normalizes paths and derives a tree/counts from Task.group.
  • Add folder selection to TaskLive.Index, reset the Task stream to the selected subtree, and track empty/count state separately.
  • Render the navigator, All tasks, and Unfiled; persist collapsed paths and last selection in local UI state or URL params.

2 · Assign and move

  • Add a dedicated Task metadata update that writes metadata.springroll.group while preserving unrelated frontmatter.
  • Support “Move to folder…” from each Task's overflow menu and folder creation from that chooser. A folder exists when at least one Task uses its path.
  • Add drag-and-drop only after the menu path works; use a LiveView hook solely for drag events, while the server owns validation and persistence.

3 · Folder operations

  • Add rename/move/delete actions as bulk Task metadata rewrites. Deleting a folder moves Tasks to its parent or Unfiled; it never deletes Tasks.
  • Stage all affected file rewrites before commit and report partial conflicts clearly. Do not silently diverge DB and SKILL.md metadata.
  • Return group from list_tasks and accept it in MCP authoring guidance so external agents preserve organization.

4 · Revisit after DB canonical

  • If users need empty folders, custom order, icons, shared permissions, folder defaults, or stable folder IDs, add a first-class folder table after Task storage phase A.
  • Until then, avoid a third operational noun and avoid coupling folder hierarchy to physical task directories.
  • Consider saved views only when cross-cutting queries—failed Tasks, expensive Tasks, tasks needing credentials—become frequent.

5 · Test the trust edges

  • Cover normalization, case collisions, ancestor counts, subtree filtering, Unfiled, and maximum depth.
  • LiveView-test selection, URL restoration, mobile drawer, stream reset, external Task updates, and move failure recovery by stable DOM IDs.
  • Ensure moves preserve slug, path, schedule, enabled state, workflow references, Runs, Outputs, and unrelated frontmatter.
Current architectural constraint: disk sync scans only immediate child directories of tasks/, deletion explicitly requires a safe direct child matching the Task slug, and workflow/MCP references use slugs. Mirroring the visual tree into nested filesystem directories would cut across all three safety assumptions. Keep the tree virtual.

Final recommendation

Build first

A quiet folder navigator inside Tasks

Use Direction A. It gives arbitrary organization without changing Spring Roll's center of gravity. The default screen remains a trustworthy Task list; the tree simply scopes it.

Ship read-only grouping first, then Move to folder, then drag-and-drop. Use the existing group metadata as a slash-delimited virtual path and keep the physical task bundle layout flat.

Deliberately defer

  • Tasks nested under Tasks.
  • Folder-level schedules or inherited settings.
  • Multiple folder membership.
  • Manual ordering, icons, and colors.
  • Saved custom views and enterprise teamspaces.
  • Nested physical directories under tasks/.
