Recipes and reports

merging the feed and the source list · four structures + a naming study

1 and 2 aren't alternatives — they're two halves of one thing. Every reader ever built has a source list and a stream: Mail has mailboxes and messages, NetNewsWire has feeds and articles, Sentry has projects and issues. Model 1 kept the stream and exiled the sources to another page. Model 2 kept the sources and never built the stream. That's the scatter — each one is a reader missing a limb.

Put them back together and the whole Tasks-vs-Runs question dissolves into one selector on one surface: nothing selected shows everything (that's model 1), a recipe selected shows that recipe (that's model 2). Below are four ways to build that, from most structure to least.

Fix the vocabulary at the same time — half the scatter is linguistic. "Run" is a verb doing double duty as a noun, which is why "Tasks" and "Runs" read as two settings screens rather than a source and its output. Demote it: run stays a verb ("Run it now"), and the noun becomes what the thing actually is — a report. Then the two words in your nav name genuinely different kinds of object: Recipes (what you wrote) and Reports (what came back).

Recipe earns its place beyond the pun. A recipe is exactly this shape: ingredients (model, integrations), method (the instructions), yield (the declared outputs), and how often you make it (the schedule). That's the same four-slot anatomy from the earlier study, with a name that explains it.

A · The reader — source column beside the stream, both always visible

Prior art: Mail.app and NetNewsWire (mailboxes/feeds beside the message list) · Sentry (project selector beside issues)

The literal merge. "All reports" is selected by default, so the home page is model 1's feed. Click a recipe and the same stream narrows to that recipe's history — model 2, without a second page or a second concept. The column doubles as the library: unread counts, health dots, and a New recipe button.

Fixes: one surface, one selector, zero "which page do I go to". The source column is the library — you never navigate to it, it's just always there, which is exactly how a reader treats feeds.

Costs: three columns including the app rail. That's a lot of vertical furniture for an editorial app built on one centered column, and it breaks the max-w-4xl rule outright. Mobile has to collapse the source column into a sheet.

B · One column, source strip — the same merge, without the third column

Prior art: Apple News topic chips · Slack's unread filters · any "All / by source" tab bar

The selector collapses from a column into a row of chips at the top of the stream. Same behavior — All is the feed, a chip is one recipe's history — but the page stays a single centered column and the layout rules survive intact. The chip row is also where the library lives: the last chip is All recipes ›.

Fixes: everything A fixes, inside the layout you already have. The chip row makes the recipe set visible at a glance without a page for it, and "Needs you" gets to be a filter rather than a red word buried in a row.

C · One page, two zones — today's reports on top, the recipe shelf beneath

Prior art: Apple News (top stories, then your channels) · Spotify home (recent, then library shelves) · Things 3 (Today, then the lists)

The most direct answer to "what page do I actually focus on": there is one page. The top zone is the stream, the bottom zone is the library — both on the home scroll, no selector at all. Recipes stay visible every day, so nothing goes invisible the way it does in a pure feed.

D · Two page types, nothing else — the stream, and the recipe. A report is a section of a recipe.

Prior art: GitHub Actions (a run lives inside its workflow) · podcast apps (an episode belongs to the show page) — combined with the feed as the front door

The strongest simplification available: the app has exactly two destinations. The stream (any of A–C) is the front door, and everything you click lands on the recipe, opened to that day's report. Recipes index, runs index and run detail all collapse into this one page. Below is that page — and it's where "recipe" stops being a pun and starts being the information design.

Fixes: four page types become two. The recipe page carries the anatomy (uses / model / produces / schedule / method) in one place, so the stream row never has to. And a failing recipe explains itself on the page you'd naturally land on, rather than in a list row.

One caution worth weighing: "recipe" implies something you make once from a fixed procedure, and yours run on a schedule forever and produce a fresh answer each time. That's closer to a standing order than a recipe. It still works — a recipe is a thing you cook weekly — but if the word ever feels wrong, that mismatch is why.

Where I'd land

B + D, with C as the fallback if you want one nav item. B gives you model 1's stream and model 2's source selection in a single centered column that doesn't break your layout rules — it is the merge with the least new machinery. D is what makes it stick: every click lands on the recipe, so the anatomy, the history and the failure explanation all live in one place and the stream row stays three quiet lines.

Two things this direction requires that today's data doesn't have: reports need their own headline (a one-line title in the response contract, so the stream isn't seven rows all named after their recipe), and a report needs a read/unread state, which is the thing quietly doing the work the seven bars were failing to do.

If you want, the next study can take just B and D and push them through the real edge cases — forty recipes, a day with nothing scheduled, a recipe that has never run, and mobile.
