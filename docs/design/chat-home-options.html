Where threads live

The Inbox is doing two jobs at once, and there is no way to say “start a new one.” Four ways to give chat a home, four ways to make a fresh thread, and a recommendation for what to build first.

Preview mockups in

The problem

Two records, sorted on the wrong axis

Today the Inbox interleaves scheduled runs and chat sessions by time, and offers All · Scheduled · Asked to un-mix them. Reaching for a filter to separate two things is the evidence they were wrongly mixed. They differ on an axis that matters more than when they happened: what you are supposed to do with them.

A run is mail

It arrived while you were away. You read it once, and it is finished. Its value is in the arrival — a stack sorted by time is exactly right, and unread is the only state worth tracking.

A thread is a document

You started it and you are mid-way through it. Its value is in returning to it — sorted by time it sinks out of reach in a day, and “read” means nothing, because you wrote it.

The model still holds

“A run is a templatized chat” is right about the engine and right about starting. It was never a claim that both belong in one sorted list.

The second complaint has a concrete cause in the code. Whether an ask makes a new thread or extends an old one is currently a property of the URL, with no override: askBarScopeForPath returns a continueSessionId on /chat/:id, so the bar always extends that thread; everywhere else the entry hits create-or-resume, so asking from a run detail silently re-opens the thread that already exists for that run. Neither default is wrong. There is just no way to say otherwise.

Part one

Four homes for chat history

Each mockup assumes the same thing underneath: chat history is never deleted. What changes is the surface you return through.

A

Two lanes on one page

Cheapest · good fallback

Inbox keeps its day-group cards for runs. Open threads move into a slim strip pinned above them — receipt height, capped at four, ending in All threads →. The segmented filter is deleted: nothing to filter once the two kinds never interleave.

  • +Nothing new to learn. Same page, same rows, one strip.
  • +Keeps the no-chat-tab rule and keeps live threads visible where you already look.
  • −Still one page doing two jobs — quieter, but the concept is unchanged.
  • −The strip has a ceiling. Past four open threads it needs its own page anyway.

B

The bar remembers

Recommended

Inbox goes back to being runs only. History hangs off the ask bar instead of a page: ⌘K — or the chevron at the bar's right — opens the standard popover shell upward, listing recent threads with New thread pinned at the bottom and All threads → below it.

This is the strictest reading of the accepted rule. If chat is the input layer and not a destination, its history belongs to the input — available identically on every page, including from inside another thread.

  • +The Inbox becomes legible again — one kind of record, no filter.
  • +Works from everywhere, so “I'm on a run page and want a separate chat” is answered in the same gesture as “where was that thread.”
  • +New thread gets a permanent home at the bottom of the list.
  • −Discoverability. A keyboard-first surface is invisible until found — the chevron and an empty-bar hint have to carry it.

C

Threads becomes a tab

Only if the product moved

Nav grows a fourth destination: Inbox · Threads · Recipes · Integrations. Threads gets what a real index gets — search, pinning, grouping by subject, an archive.

Worth naming honestly: this reverses the accepted decision, and it does so on real evidence — you keep wanting things chat is good at. The cost is identity. The home of a scheduler is its mail; a chat tab beside it starts to read as a chat app that also has cron.

  • +Zero ambiguity and unlimited room to grow — search, pins, folders.
  • +“New thread” is obvious — it's the primary button on its own page.
  • −Dilutes the pitch. Four tabs, and the differentiated one is no longer first among equals.
  • −Invites a chat-first habit, which is how the scheduler stops being used.

D

One feed, two densities

Fixes volume, not concept

Keep the union exactly as designed, but let threads change shape as they settle. A live or unanswered thread holds a full row. Once it resolves it drops to receipt height, and a day's worth of resolved asks collapses into a single 6 asks row you can open.

This is the smallest possible change and it does solve silting. It does not solve the thing that made the page feel confusing — mail and documents are still one list.

  • +Nothing moves. No new surface, no reversed decision, one row renderer.
  • +Chronology survives — the thread stays next to the run that caused it.
  • −Two row heights on one list is its own kind of noise.
  • −Returning to an old thread still means scrolling a mailbox.

Part two

Saying “start a new one”

These are independent of Part One and can ship in any order. Each attacks the same defect from a different side: today the app decides new-versus-continue for you, based on which page you happen to be standing on.

1

The scope chip becomes a control

Ship this first

Right now the origin tag is a label that appears after the fact, on the thread page. Move it into the bar on subject pages and make it a menu: ◦ Morning digest ▾ → this run · its recipe · Springroll (no scope).

One control, two problems solved. It shows you what the ask can see and change before you send it, and dropping to Springroll gives you a plain unscoped chat without leaving the run you're reading.

  • +Makes scope visible before sending, which is worth doing regardless.
  • +Reuses the popover shell — no new floating grammar.
  • −Adds an element to a deliberately thin bar. It should only appear when a scope actually applies.

2

New by default, continue on purpose

Recommended

Invert create-or-resume. Asking from a run detail always opens a new thread scoped to that run. When an earlier thread about the same subject exists, one quiet line sits above the bar: Continue “Why did this fail?” · 2h ago →.

Silent resume is what actually surprises people — you type a fresh question and get an answer coloured by a conversation you had on Tuesday. Starting fresh is cheap and obvious; continuing should be the deliberate act, not the invisible default.

  • +Removes the surprise without removing the convenience.
  • +Small, contained change — pass mode: "new" and render one link.
  • −More threads per subject. Only tolerable if Part One gives them a decent home.

3

A new-thread key that works inside a thread

Cheap, ship with 2

On /chat/:id the bar is the reply composer, and that is correct. Add a ＋ where the model trigger sits, plus ⌘N: start a fresh thread that inherits the current thread's scope, and carry the text you already typed across with you.

The draft carry-over is the part that matters. The moment you notice you're in the wrong thread is usually the moment you've already typed the question.

  • +Answers the complaint literally — a new chat while standing in a chat.
  • +⌘⇧N can mean the unscoped version, from anywhere in the app.
  • −Inheriting scope is a guess. Pair it with the chip from 1 so the guess is visible and correctable.

4

Branch from here

Later, if you miss it

A per-message action that opens a new thread carrying a link to the parent turn rather than the transcript. For “this went sideways, start clean, but keep the pointer.”

The reason to prefer a link over copied context is the thing already on your backlog: context is the expensive resource in a tool loop. A branch that inherits the whole transcript inherits the whole bill.

  • +Escape hatch for a polluted thread that doesn't lose the trail.
  • −Needs a parent link in the data model and a way to render it.
  • −Not the reported problem. Don't build it until 1–3 are in use.

Part three

Making chat belong to a scheduler

This is the part that decides whether general chat feels bolted on. Chat earns its place when the things you discover in a thread can become scheduled work without retyping them.

bridge
Schedule this thread

An action in the thread's footer that opens the recipe composer prefilled from the conversation — prompt, model, and whichever connections the thread actually touched. The thread becomes the draft.

bridge
“Do this every morning”

Said inside a thread, that sentence should create the recipe through the app tools and answer with the recipe card — never bounce you to a form. Forms stay the fallback.

lifecycle
Threads need an end

Without a settled state, history becomes a landfill. Idle for 24 hours with no pending question, and a thread settles into history on its own; an explicit Done does it immediately.

naming
Retire “Asked”

It's a filter word, and it only exists because the two record types share a list. The code already says thread everywhere — thread-head, thread-chip. Let the UI say it too.

If it were mine

Runs-only Inbox, history on the bar

  1. Take the chats out of the Inbox. Inbox becomes scheduled runs and nothing else, and the All · Scheduled · Asked switch is deleted. It is one page again with one job: what happened while you were away.
  2. Give history to the bar (B). Recent threads, New thread, and All threads → in the popover shell you already have, opening upward from the launcher, on every page. Chat stays the input layer; the input layer grows a memory.
  3. Make new the default and scope explicit (2 + 1). Asks start fresh; a quiet Continue… link appears when there's something to continue; the scope chip in the bar says what the ask can reach and lets you drop it to plain Springroll.
  4. Keep A in your pocket. If two weeks of dogfood say the bar's history is undiscoverable, the open-threads strip on the Inbox is a half-day change and completely compatible with everything above.
  5. Only reach for C if the answer changed. A Threads tab isn't wrong — it's a different product claim. Make it deliberately, with evidence, not because the history list got long.
?

Does an unscoped thread still know about Springroll? “No scope” should mean no subject, not no tools — you still want to ask what your recipes are. Worth stating in the chip's copy so it never reads as a downgrade.

?

Where do run replies land? Replying to a letter continues the run as a thread, which means the run row and the thread are the same record. If Inbox is runs-only, that thread stays visible on the run — good — but it should also appear in the bar's recents, or you'll lose it.

?

Is ⌘K taken? If the model picker or a future command palette wants it, the bar's history should own the chevron and let the palette own ⌘K. Decide before muscle memory forms.
