Springroll internals

How tools get loaded.

Three systems, one problem: don’t dump hundreds of API operations into the model every turn. Open this file and walk the story. The important split is what sits in the tool list versus what later shows up in the transcript.

The three buckets

Forget “lazy” for a second. Watch three places.

A model turn has a tool list (the menu of things it can call) and a transcript (everything already said, including earlier tool results). Executor adds a third place: a sandbox the model writes code into.

Bucket A · tool list

Sent every turn as available tools

If a schema is here, the model pays for it on every step — even if it never calls it.

Bucket B · transcript

Dumped in after a discovery call

Activate/describe results land here. Later steps re-read them. Cheap at first, expensive if the chat goes long.

Bucket C · sandbox

Executor only

The MCP client advertises one tool, execute. Search and schemas live inside the sandbox, not in Springroll’s tool menu.

So is Springroll lazy?

Yes for connectors in chat. No for app tools. No for runs.

Chat connectors Chat app tools Recipe runs Executor
Schemas in Bucket A by default? No Yes · all ~30 Only the pins No · only execute
How a schema appears activate/describe → transcript Already there Pinned at recipe save tools.describe inside sandbox
How a call happens call_read_connection_tool({connectionId, toolName, input}) Direct create_task etc. Direct run_sql({sql}) tools["neon.run_sql"](input) in JS
Still lazy on step 8 of a long chat? Menu yes · transcript no No N/A · short known set Menu stays one tool

The backlog card “Load Springroll app tools on demand in chat” is the remaining gap: chat would start with a core set plus search_application_tools, instead of all ~30 Springroll tools every turn. Connector discovery already works that way.

The call shape

Why chat uses wrappers and runs don’t.

Chat cannot put every connected tool on the menu — catalogs are huge and change after sign-in. Runs already chose a small allowlist, so the model gets real named tools and the host can pin schema hashes.

Chat

search names → activate 1–10 schemas → call_read_connection_tool → host injects key + policy

Run

recipe pins run_sql → open Neon session → verify schema hash → model calls run_sql

Executor

execute → sandbox tools.search → describe one path → call; host attaches secret

If you remember one picture

Chat hides catalogs. Runs freeze them. Executor hides everything behind execute.

  1. Springroll chat is lazy at the menu. Neon is not a tool the model can pick from the list. Discovery wrappers are.
  2. It is not lazy in the transcript. Once activated, those JSON schemas ride along for the rest of the thread.
  3. Springroll runs are eager on purpose. Unattended work should not rediscover a 200-tool catalog every morning.
  4. Executor is lazy at the MCP surface. Other agents never see Stripe’s 500 operations as native tools.
  5. App tools in Springroll chat are still eager. That’s the open todo — not connector loading.
