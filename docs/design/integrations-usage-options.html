Two species, and a graph.

Second pass, on two premises from the first round. One: a connected account and a one-click connector are not the same object, so they should not be the same card. An account has an owner, scopes, a health state and a history; a connector has a name and a button. Making them share a card shape is what forced the 160px of whitespace on the tiles that had nothing to say.

Two: the thing an account has to say is its usage. Springroll already draws that — ActivityTrail in turn-meter.tsx, one tick per tool call, green for clean, warn for a repeat, danger for a failure, height carrying weight. Reusing it on the integrations tab means a connection is described in the same visual language as the runs and chats that consume it.

00The bar graph, three readings

Same ticks, same colors

3px ticks, 2px gaps, 1.5px radius, --ok / --warn / --danger — lifted straight from .activity-tick. Only the tick size changes with surface; the vocabulary never does.

ALive cards, add strip

The idea

Only connected accounts get cards, and the card is mostly graph: 21 days of calls, the count, failures, scopes. One-click connectors stop being cards entirely — they are pills in a strip, because one click is a button, not a tile.

Why it works

Nothing has to be padded to match anything. A brand-new connection with no history shows an empty trail and says so, which is information rather than dead space.

BTelemetry ledger

The idea

Accounts become rows in a metrics table — trail, calls, failures, last used in fixed columns, so the graphs line up and can be compared down the column instead of hunted for card by card.

Why it works

A shared baseline is what makes small bar charts readable. Ragged card placement destroys that; a column preserves it. The catalog sits below as tiles — again a different species, and visibly lighter.

CUsage wall

The idea

The graph is the card. Each account is a panel with two headline numbers and a full-bleed 21-day chart along the bottom edge — the connection presented the way a run is: activity first, chrome second.

Why it works

Loudest of the four, and the only one where a dead integration is impossible to miss. Catalog drops to a 6-up strip of small squares so the wall stays about what is running.

DPer-tool breakdown

The idea

Instead of one graph for the connection, a bar per tool: which three tools this integration actually calls, how often, and which are failing. The card explains what the integration does for you, not just that it is alive.

Why it works

It is the same data the permissions screen needs — a tool nobody calls is a scope you can drop. Adding collapses to one row, since browsing is a rare act next to auditing.

EWhat this needs from the backend

The data

Every direction here needs one new thing: tool calls attributed to a connection, over time. Runs already persist RunToolCallSummary (tool name, status, timings) and chats persist chat_tool_calls — what is missing is the connection id on each row and a daily rollup to read back per card.

The cheap version

If the rollup is not worth it yet, direction A degrades gracefully: ship the card with last-used and tool counts, draw the trail from the most recent 21 calls rather than 21 days, and the layout never changes when real history arrives.

Recommendation

A for the tab, D on the detail page. A gives every connected account a card that is mostly signal, and demotes one-click connectors to the pills they always were. D’s per-tool bars then answer the next question — which scopes you can safely drop — where there is room for it.

Either way

Two card species, one graph vocabulary. A connector that has never run has no graph and no card — just a pill. Nothing on the page is padded to match anything else.
