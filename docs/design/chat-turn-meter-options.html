Turn meter — four ways to show what's happening

Option D folded the loop away; this adds the context back without unfolding it. Every example uses your real Firebase turn: 23 steps, 36s, 130,235 tokens, $0.0248 — and seven redundant Inspect connections calls that the old pill stream buried.

Note on Stop: the ask bar already carries one while a turn runs. A second Stop on the meter is worth it only because the bar is fixed at the bottom and the meter is where your eye already is — but they must never disagree, so both drive the same cancelChat call.

Option A

Tick trail — one mark per tool call

A row of 3px ticks, one per step, colored by outcome and filling left→right as the turn runs. It's the recipe card's run-trail grammar applied to a single turn: shape carries the count, color carries the errors, and a glance tells you a 23-step turn from a 3-step one. Optional amber tick marks a repeat of a call already made.

Option B

Cost gauge — where the tokens went

A thin segmented bar splitting the turn's tokens into cached, fresh input, and output, sized against a reference turn. It answers "why did this cost 8¢?" — a cache-miss-heavy turn looks visibly different from a long-output one. Weaker on activity: it says nothing about steps failing.

Option C

Counter strip — no graphics at all

Everything as mono telemetry, errors in danger color, nothing drawn. Most faithful to "mono is telemetry, color is meaning" — and the only option with zero new visual vocabulary. It scales to any step count and reads identically at every width.

Option D

Time bars — where the 36 seconds went

One bar per step, height proportional to its duration. This is the diagnostic view: a single 18-second web fetch looks nothing like twenty 300ms connection checks, and a stalled step grows while you watch it.

What each one costs to build

  • Tick trail + counters (A + C). Everything needed is already in the message parts — one tick per tool part, danger when the result tone is danger, amber when an identical (tool, input) pair appeared earlier in the turn. No new server data.
  • Stop on the meter. Reuses the ask bar's existing cancelChat + stop() path; the meter just needs the handler passed down. Only rendered while the turn is live.
  • Cost gauge (B). ChatUsageDto already carries cachedInputTokens, inputTokens, and outputTokens — but usage lands on the turn only at the end, so the live half needs per-step usage the client doesn't get yet.
  • Time bars (D). Needs per-step start/finish timestamps. The parts don't carry them; this is a server change, so it's the one option that isn't free.
  • Live counters generally. Tokens and cost during a turn need the same per-step usage as B. Until then the live line can honestly show tools, errors, and elapsed — and hold tokens/cost until the turn closes.
